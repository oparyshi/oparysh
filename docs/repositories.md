# Репозитории oparysh

Репозиторий oparysh — это статический каталог из **рецептов** (`pkg.toml`),
**тарболов исходников** (`dist/`) и **индекса** (`index.toml`). Никаких скриптов
и установленных пакетов внутри репо не хранится: всё собранное клиент соберёт
сам. Репозиторий можно раздавать по HTTP(S) как обычную статику или
использовать как локальный каталог — для тестов, оффлайн-машин и приватных
репозиториев.

Формат рецептов подробно описан в [`DOCS.md §5`](../DOCS.md#5-формат-рецепта-pkgtoml);
здесь — только то, что нужно владельцу репозитория.

---

## 1. Структура репозитория

```
my-repo/
├── index.toml                    # генерируется, НЕ правится вручную
├── recipes/
│   └── <name>/<version>/pkg.toml # по одному каталогу на каждую версию
└── dist/
    └── <name>/<version>/<name>-<version>.tar.gz   # тарболы исходников
```

Требования:

- рецепт каждой версии лежит в `recipes/<имя>/<версия>/pkg.toml`;
- тарбол — в `dist/<имя>/<версия>/`, имя файла должно совпадать с
  `[source].file` в рецепте;
- в `[source]` рецепта обязательно указан `sha256` (см. [Целостность](#5-целостность)).

Необязательный файл `database.tar.zst` (снапшот для оффлайн-синхронизации
репозитория) при наличии указывается в конфиге клиента через `snapshot`.

## 2. Пример: минимальный репозиторий с одним пакетом

```
my-repo/
└── recipes/myapp/1.0.0/pkg.toml
```

`recipes/myapp/1.0.0/pkg.toml`:

```toml
[pkg]
name     = "myapp"
version  = "1.0.0"
build    = 1
arch     = ["x86_64", "aarch64"]
desc     = "Пример приложения"
license  = "MIT"

[source]
url     = "https://example.org/myapp/myapp-1.0.0.tar.gz"
sha256  = "<sha256 тарбола>"   # ОБЯЗАТЕЛЬНО
# или: file  = "dist/myapp/1.0.0/myapp-1.0.0.tar.gz"  # тарбол прямо в репо

[deps]
build = ["make>=4.0", "gcc>=11"]     # нужны только при сборке
run   = []                            # нужны в рантайме

[build]
system = "autoconf-make"

[build.install]
prefix = "/usr/local"

[files]
unknown_warn = true
```

Собираем тарбол и кладём его в `dist/` (если источник — файл в репо):

```sh
mkdir -p dist/myapp/1.0.0
tar czf dist/myapp/1.0.0/myapp-1.0.0.tar.gz myapp-1.0.0
```

## 3. Типы сборки и поле `build`

В рецепте есть два разных «build» — их часто путают:

### 3.1 `build = 1` в `[pkg]` — ревизия рецепта

Это просто **счётчик пересборок той же апстрим-версии**. Если вы меняете
патчи, флаги сборки или другие части рецепта, не трогая `version`,
увеличивайте `build` на 1. Клиент сравнивает её с установленной ревизией:
`build > installed.build` → пакет предлагается к пересборке при `upgrade`.
Никакой логики сборки это поле не задаёт (подробности —
[§6 Целостность](#rebuild-при-той-же-версии)).

### 3.2 `system = "..."` в `[build]` — тип сборки (сборочная система)

А вот это флаг, который определяет, **как именно** клиент собирает пакет.
Поддерживаются:

| `system` | Действия по умолчанию |
|---|---|
| `autoconf-make` | `./configure --prefix=$PREFIX` → `make` → `make install DESTDIR=` |
| `cmake-ninja` | `cmake -G Ninja -DCMAKE_INSTALL_PREFIX=$PREFIX` → `ninja` → `ninja install` |
| `cargo` | `cargo build --release` → `cargo install --root=$DESTDIR/$PREFIX` |
| `meson` | `meson setup --prefix=$PREFIX` → `ninja` → `ninja install` |
| `make-only` | только `make` / `make install` |
| `custom` | команды берутся строго из `[build.steps]` |

- Если рецепт не задаёт `system` явно — используется `autoconf-make`
  (наиболее распространённый случай для C/C++ проектов).
- `system = "custom"` требует увидеть `[build.steps]` с шагами
  `prepare`/`compile`/`install`; без него рецепт невалиден.
- Любой рецепт можно полностью переопределить шагами `[build.steps]`
  независимо от `system` (полное переопределение команд).
- Префикс установки задаётся в `[build.install].prefix`, окружение
  (CFLAGS, CC, MAKEOPTS) клиент вычисляет из своего конфига — рецептом
  его перехватывать не нужно и нельзя.

Новый пакет часто выбирается так: проект с `configure` → `autoconf-make`,
проект с `CMakeLists.txt` → `cmake-ninja`, Rust-крейт → `cargo`,
проект на meson → `meson`, простой `Makefile` без configure → `make-only`,
всё остальное (скрипт, генератор, несколько команд) → `custom`.

### 3.3 Сборка `custom` подробно

`system = "custom"` — для проектов, которые не вписываются в стандартные
системы: собственный сборочный скрипт, cmake без ninja, генераторы кода с
последующей установкой и т.п. Команды берутся **только** из `[build.steps]`;
если секция отсутствует или пуста, рецепт невалиден.

#### 3.3.1 Формат

Каждый шаг — массив строк: первый элемент — команда, остальные — аргументы.
Команды выполняются в извлечённом каталоге исходников
(`build/<name>-<ver>/`) в порядке prepare → compile → install:

```toml
[build]
system = "custom"

[build.steps]
prepare = ["./autogen.sh", "--with-sysroot=/usr"]
compile = ["make", "${OPARYSH_MAKEOPTS}"]
install = ["make", "install", "DESTDIR=${OPARYSH_DESTDIR}"]
```

Правила:

- **`install` обязателен**; `prepare` и `compile` можно опустить (например,
  когда prepare не нужен, а compile уже вызывается из install-скрипта).
- Каждое свойство — это **один шаг с множеством команд-элементов**, а не
  список нескольких шагов; вложенные массивы не поддерживаются.
- Выполнение не интерактивно и не через shell: пайпы, `&&`, `$VAR` вашей
  оболочки внутри шагов работать не будут — для сложной логики положите
  скрипт рядом с рецептом или в тарбол и вызывайте его как команду.
- Если любой шаг завершается ненулевым кодом, сборка прерывается, лог
  пишется в `logs/`, каталог `build/` сохраняется для отладки (см.
  `--keep-build`).

#### 3.3.2 Подстановки внутри шагов

В аргументах команд доступны переменные окружения (раскрываются клиентом):

| Переменная | Значение |
|---|---|
| `${OPARYSH_PREFIX}` | префикс установки из `[build.install].prefix` |
| `${OPARYSH_DESTDIR}` | временный DESTDIR, откуда файлы уйдут в destroot |
| `${OPARYSH_MAKEOPTS}` | итоговые makeopts, включая `-j<jobs>` |
| `${OPARYSH_CFLAGS}` / `${OPARYSH_CXXFLAGS}` | итоговые флаги профиля + extra + рецепта |
| `${OPARYSH_CC}` / `${OPARYSH_CXX}` | выбранные компиляторы |
| `${OPARYSH_JOBS}` | количество потоков сборки |
| `${OPARYSH_SRC_DIR}` | каталог извлечённых исходников |

Также в окружении каждого шага уже заданы `CC`, `CXX`, `CPP`, `CFLAGS`,
`CXXFLAGS`, `LDFLAGS`, `MAKEOPTS`, `DESTDIR` — инструменты из тарбола
(configure, make) подхватят их сами.

#### 3.3.3 Своё окружение

Дополнительные переменные задаются в `[build.env]` рецепта:

```toml
[build]
system = "custom"
env    = { LIBS = "-lm", SQLITE_ENABLE = "1" }
```

Они действуют на все шаги. Обратно перекрыть `LDFLAGS` из шелла нельзя —
окружение сборки сужено для воспроизводимости (см. DOCS.md §12).

#### 3.3.4 Пример: cmake без ninja

```toml
[build]
system = "custom"

[build.steps]
prepare = ["cmake", "-S", ".", "-B", "build",
           "-DCMAKE_BUILD_TYPE=Release",
           "-DCMAKE_C_COMPILER=${OPARYSH_CC}",
           "-DCMAKE_INSTALL_PREFIX=${OPARYSH_PREFIX}"]
compile = ["cmake", "--build", "build", "--", "${OPARYSH_MAKEOPTS}"]
install = ["cmake", "--install", "build", "--",
           "DESTDIR=${OPARYSH_DESTDIR}"]
```

#### 3.3.5 Tips

- Не кладите в шаги `sudo`/`pip install` в систему — собирайте всё в
  `${OPARYSH_DESTDIR}`, иначе файлы не попадут в манифест и в БД, а
  `oparysh check` и удаление пакета не увидят этих файлов.
- Скрипт prepare-этапа, если он свой, лучше приложить к рецепту (та же
  папка `recipes/<name>/<ver>/`) и проверить его sha256 через
  `[[patches]]`-механику или держать в тарболе.
- Для сборки, где нужен только `make install` по своему Makefile, чаще
  подходит `make-only` + `[build.env]`, чем `custom`.

## 4. Генерация index.toml

Индекс собирается утилитой **`oparysh-repo-index-gen`** (крейт
`contrib/repo-index-gen`; устанавливается как отдельный бинарник или собирается
вместе с workspace). Вручную `index.toml` править не нужно — он всегда
перегенерируется.

```sh
cargo install --path contrib/repo-index-gen    # или просто cargo build --workspace

oparysh-repo-index-gen <DIR> --name <имя> [опции]
```

```
oparysh-repo-index-gen $HOME/www/my-repo \
    --name stable \
    --origin https://repos.example.com/stable \
    --updated 1770000000          # хотите воспроизводимые сборки — фиксируйте!
# -> $HOME/www/my-repo/index.toml
```

Опции:

| Флаг | Значение |
|---|---|
| `--name` (**обязателен**) | имя репозитория `[repo].name` — то же имя будет в конфиге клиента |
| `--origin` | origin, пишется в `[repo].origin`; для HTTPS-репо — его URL |
| `--updated` | unix-время (сек); для воспроизводимости ставьте фиксированное |
| `--output` | куда писать `index.toml` (по умолчанию `<dir>/index.toml`) |

### Что кладётся в индекс

Для каждого пакета в `[pkg]`-записи дублируются метаданные рецепта плюс **два
обязательных хэша**:

| Поле | Что это | Откуда |
|---|---|---|
| `recipe_sha` | sha256 файла `pkg.toml` этой версии | считается по рецепту |
| `src_sha256` | sha256 тарбола из `dist/` | считается по тарболу |
| `deps` | run/build-требования (для быстрого ресолва без загрузки рецепта) | merge `[deps]` рецепта |
| `provides` / `conflicts` | виртуальные алиасы и конфликты | из рецепта |
| `tags` / `arch` / `desc` | для `search`/`info`/фильтров | из рецепта |

`[[pkg]]`-записей в индексе столько, сколько версий пакетов в `recipes/`.

## 5. Публикация

### Локальный каталог

Просто укажите путь в конфиге — tar/HTTP не нужны, но файлы должны существовать
на диске. Используется для тестов, оффлайн и приватных репозиториев
(`tests/fixtures/mini-repo` в этом проекте — как раз такой пример).

### HTTP(S)

Разложите каталог на любом static-хостинге:

```sh
# всё дерево my-repo доступно как https://repos.example.com/stable/
rsync -av --delete my-repo/ webserver:/srv/repos/stable/
# или просто коммитьте и публикуйте через git
```

При изменениях всегда **сначала перегенерируйте** индекс, потом выгружайте всё
вместе: иначе клиент может получить обновлённые тарболы со старым файлом
`index.toml` (или наоборот) и уйдёт в sha256-mismatch. Атомарная публикация
(rsync в staging + смена symlink, или версия-ветка в git) убирает опасность
«полусобранного» индекса для тех, кто синхронизируется посреди публикации.

## 6. Целостность

Проверяются **все** артефакты по цепочке (см. [`DOCS.md §9`](../DOCS.md#9-целостность-и-sha-256)):

| Артефакт | Хэш | Когда проверяется клиентом |
|---|---|---|
| тарбол исходника | `[source].sha256` рецепта | при download-extract сборки |
| файл рецепта | `recipe_sha` | при загрузке рецепта из репо |
| тарбол из `dist/` | `src_sha256` | при скачивании из репо |
| каждый установленный файл | в БД | `oparysh check` |

### Rebuild при той же версии

Если пересобираете пакет при неизменной апстрим-версии (новые флаги сборки,
переезд патчей) — **не меняйте `version`**, увеличивайте `build` в рецепте на
`+1`: `oparysh upgrade` увидит `build > installed.build` и пересоберёт пакет
по новой записи индекса.

### Подписи (опционально)

Если у репозитория в конфиге клиента указан `key`, то `index.toml` должен быть
подписан detached-подписью `index.toml.sig` тем ключом, который указан в
`key = "/etc/oparysh/keys/stable.gpg"`. Клиент проверяет подпись при каждом
`sync`; несоответствие = отказ работы с репо.

## 7. Подключение репозитория на машине-клиенте

```sh
# в конфиге /etc/oparysh/oparysh.conf
[repositories]
[[repositories.entries]]        # порядок задаёт приоритет ресолва (см. DOCS §7)
name = "local"                  # путь-репо
path = "/srv/oparysh-repo"

[[repositories.entries]]
name = "stable"
url  = "https://repos.example.com/stable"
# key = "/etc/oparysh/keys/stable.gpg"    # опционально, для подписанных индексов
```

Либо команды CLI:

```sh
oparysh repo add stable https://repos.example.com/stable
oparysh repo add local  /srv/oparysh-repo
oparysh repo list                  # имя, источник, пакетов, дата updated
oparysh repo del  <name>          # убрать из конфига
```

После добавления:

```sh
oparysh sync                 # скачать/обновить index.toml
oparysh search myapp         # поиск по имени/описанию/тегам
oparysh info myapp           # метаданные пакета, зависимости
oparysh install myapp        # соберёт и установит (спросит подтверждение)
```

## 8. Частые ошибки владельца репо

| Симптом | Причина | Лечение |
|---|---|---|
| «не каталог репозитория: отсутствует index.toml» / «отсутствует каталог recipes/» | индекс не собран или репо выложено не целиком | `oparysh-repo-index-gen <dir> --name …` и полная публикация дерева |
| «sha256 mismatch при install/upgrade» | тарбол обновили, а индекс не перегенерировали | перегенерация индекса после каждого релиза |
| клиент видит старую версию | обновили `recipes/`, но не перегенерировали индекс | снова перегенерация; при той же апстрим-версии повышайте `build` (см. ниже) |
| «ERROR: активный профиль `X` не найден в конфиге» | у клиента нет `[profile.X]` в `oparysh.conf` | это не проблема репо: предупредите клиентов в README репо |

## 9. Проверка репо перед публикацией

```sh
cd /path/to/my-repo

# 1. индекс свежий и сходится с деревом (имя то же, что в реальном индексе):
oparysh-repo-index-gen . --name <реальное-имя> --output /dev/stdout | diff - index.toml && echo OK

# 2. локальный клиент видит его:
oparysh repo add check $PWD && oparysh sync && oparysh repo list && oparysh search /

# 3. сборка хотя бы одного пакета из репо:
oparysh build <name>/<ver> --install --yes && oparysh check
```

Готовый образец минимального репозитория — фикстура
`tests/fixtures/mini-repo` в дереве oparysh.
